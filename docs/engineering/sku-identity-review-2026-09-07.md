# Duplicate SKU identity safeguards

Two different products can share a merchant SKU code. Previously, the single-history lookup selected the first matching catalog row while the batch lookup kept the last. A retired CSV product could therefore supply a current Shopify variant's detail forecast, and two active variants could disagree between the action feed, forecast list, detail forecast and reorder plan.

The shared `shop_skus.build_sku_alias_index(db, shop_id)` now resolves a code using inventory ownership. Exactly one product with any Inventory row is authoritative, including a zero-quantity row. If no candidate has inventory, exactly one historical catalog candidate remains usable for history-only CSV workflows. Multiple eligible candidates raise `AmbiguousSkuError` from single-item resolution. Batch history reads omit ambiguous aliases; they never substitute another product's history or report those omissions as recorded zero sales. Raw catalog, stock, orders and SKU strings are unchanged. Co-purchase scoring uses only the uniquely resolved product owner of each alias, so a retired CSV row cannot be recommended as a bundle with its current native owner. The shop-wide historical order denominator is retained; unique history-only products still contribute evidence.

Read projections add `product_id`, `identity_ambiguous` and `identity_warning`. The product ID is an internal row identity for rendering and selection; supplier-facing SKU fields retain their existing strings. Raw-alias detail endpoints return HTTP 409 for ambiguity. Feeds expose `identity_issues` with the affected product, name, SKU and recorded on-hand quantity so an empty recommendation list cannot imply healthy inventory.

Ambiguous products remain visible as review actions and unavailable forecasts (`demand_signal="ambiguous_identity"`). No automatic reorder, recommended PO, buying-calendar recommendation, liquidation, dead-stock pairing, transfer, SKU-trigger alert or bundle-component quantity is generated from a held identity. Held action planning fields have canonical nullable `planning_values` with `planning_values_known=false`, and financial estimates are unknown. Legacy numeric fields remain for compatibility and are not authoritative while the corresponding availability flag is false. Stock, recorded recent sales, revenue contribution and inventory-value aggregates retain every active product row. Incomplete recommended spending/risk totals are marked unknown, with attributable usable rows retained.

Existing saved PO amounts are recorded merchant data and remain visible. Ambiguous saved line identities are annotated; they are excluded from incoming-stock netting. SKU override and PO write services preflight changes before writes, reject ambiguous changes with HTTP 409, and preserve unchanged unresolved records. See the focused write tests for full-map override retention and partial receipt rules. No historical rows are merged or reassigned automatically.

To resolve a genuine duplicate, review the products in the source catalog, assign distinct SKU codes where appropriate, and sync/import the corrected catalog. This release does not provide a historical identity migration or infer which old CSV orders belong to a later native variant. Retired rows and their evidence remain available in the database. Two active inventory rows for a CSV stub and native product are intentionally held until their inventory ownership is corrected; their quantities are not silently combined or deleted.

Verification uses isolated temporary SQLite databases, real non-admin trial sessions and HTTP routes. `python -m unittest tests.test_sku_identity` covers current versus retired identity, zero-stock active variants, history-only fallback, generated alias collisions, tenant isolation, list/detail agreement, visible holds, supplier SKU preservation, actual aggregate preservation and direct core guards. Existing CSV replay/forecast tests remain in `tests.test_forecast_provenance`; write guards are covered in `tests.test_sku_identity_writes`. No production data or external provider calls are used.
