# Skubase growth operator

The mission is ten distinct qualified merchants acquired organically. The milestone counts verified store connections, useful analysis views or captured payments after mission start. Intent leads and historical activity remain visible separately. A reported Reddit membership attempt is retained as one unverified historical observation, never a paid customer.

## Runtime and recovery

The existing FastAPI service runs an opt-in background worker (`GROWTH_ENABLED=true`) against the existing SQLAlchemy database. Standalone alternative: initialize the product database, then run `python -m app.growth.worker`. Do not start an additional worker merely for scheduling. SQL compare-and-swap claims and fenced leases support recovery; ready work, evidence, outbox intents and cost reservations survive restarts. Periodic observes/inbox checks are five minutes, discovery is two bounded queries per six hours, and executive review is once per UTC day. Missed periodic work is superseded, not replayed in a research wave.

Transient failures retry at most three attempts with backoff. Configuration/policy failures remain blocked and visible. A send with an uncertain provider result is never automatically replayed, including after the provider's idempotency retention window. Reconcile its receipt before any manual intervention. Resend's provider idempotency window is [24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys); the local outbox persists longer.

## Resource authority

Only environment configuration and authenticated owner operations grant authority. Model responses, public pages, replies and skill prose cannot enable spending, approve a contact, change the mailbox or execute code. Advertising has no execution adapter and remains disabled. Model/API budget defaults to zero; enable `GROWTH_MODEL_ENABLED` and set `GROWTH_DAILY_USD` only after an owner-approved ceiling. Reservations cover worst-case bounded tokens before network calls and remain charged when provider cost is uncertain. Routine planning, qualification and monitoring use deterministic code. Nano handles ambiguous routine classification; mini handles bounded analysis; Astra handles daily review or important uncertainty meeting the routing gate. Actual routing, tokens, latency and estimated cost are persisted. The owner can record evidence-linked comparisons at `POST /growth/usage/{id}/assessment`; routing incorporates the observed benefit after at least five comparable assessments. Escalation benefit remains unknown before those observations.

## Mailbox

The dedicated business inbox is `info@skubase.io`, hosted by Resend receiving. It is not the owner's personal mailbox. `CONTACT_TO_EMAIL`, magic-link sender/reply-to and waitlist sender/reply-to use that address. Receiving requires the domain's apex MX to point to Resend; outgoing domain DKIM/SPF remain intact. A dedicated secret `GROWTH_RESEND_API_KEY` supports inbound reads and sends. The signed `/growth/webhooks/resend` endpoint uses `GROWTH_RESEND_WEBHOOK_SECRET`; five-minute inbox polling is a recovery path.

Enable `GROWTH_EMAIL_ENABLED` only with a legitimate business footer (`GROWTH_POSTAL_ADDRESS`), working inbound and known provider marginal cost. Five first contacts/day is the initial cap. Only verified contacts with documented business-contact/request basis enter dispatch. Public research is not automatic permission to post in a community. There are no automatic silence followups; negative replies, unsubscribes, complaints and delivery failures suppress future sends. One requested setup-help reply is allowed; substantive questions requiring verified answers are owner obligations. Contact forms reach the business inbox independently of outreach enablement.

## Owner operations

Sign in as an existing admin and open `/growth`. The authenticated HTTP API offers evidence pagination, pause/resume, safe retries of blocked draft work, qualification with fact sources, and skill revision activation/rollback. Admin identity comes from existing authentication; no new public admin token. `/growth/events` accepts a constrained list of diagnostic events, never client assertions of purchase or store connection. Analysis views require an authenticated browser and recent usable data delivery for the same store. Demo/admin activity is excluded. Attribution persists for 30 days in first-party storage, respects Do Not Track, and excludes URL query data except named UTM fields.

`POST /growth/product-review` releases an acquisition hold with retained verification evidence and a written resolution. Contact-form submissions are delivered to `info@skubase.io` and recorded as support obligations; they do not grant outreach consent. PostgreSQL schema creation shares a transaction advisory lock between API startup and standalone initialization to avoid concurrent DDL races. See [PostgreSQL advisory locks](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS).

Memory is divided into working, strategic, customer, channel, attribution, economics and beliefs; raw evidence/contact/message/experiment/usage tables stay separate. Model context retrieves a maximum of 12 recent relevant records by default rather than the whole history. Skill JSON declares purpose, inputs, tools, process, output, success, failure and expected cost. Proposed versions require cited evidence and validation; owner activation is reversible and never edits runtime code.

## Measurement limits and development workflow

Shopify subscription activation can include a free trial. It is not payment evidence. Signed live Stripe invoice receipts support captured-payment events and recurring amounts when supplied. Shopify captured-payment receipts are not yet integrated, so Shopify MRR/payment remains UNKNOWN rather than inferred from an active subscription. CAC, retention and LTV remain unknown without sufficient attributed billing evidence. Raw first-party visits are unverified diagnostics and must not drive customer claims.

Product feedback is evidence plus a hypothesis and recommended action; downstream bottlenecks hold new outbound. Product changes require the existing development/review workflow. Public opportunity discovery currently supports bounded Shopify Community reads and attributable evidence imports; it does not automate Reddit posting, resolve every merchant's private contact identity, or bypass channel restrictions. These are explicit capability limits.

## Verification

Run `python -m unittest discover -s tests` from `backend`; `npm run build` and `npm run typecheck` from `frontend`. `tests/test_growth.py` exercises an isolated simulated full loop: opportunity → selected experiment/draft → provider receipt → restart → human reply → evidence/experiment update → changed future allocation → next assistance action. It also covers leases, duplicate prevention, suppression, ambiguous sends, spend ceilings, hostile source data, skill rollback and authorization. These fixtures are not customer acquisition evidence. `tests/growth_preview.py` provides a localhost-only visual fixture and must never be used as a production entry point.

After deployment, explicitly run `python -m app.growth.seed_live` once to retain attributed public market observations, counterevidence and the first calculator experiment. Re-running is idempotent. The calculator's success metric is an attributed connected store, not calculator use. Publishing the calculator and reading public evidence are real permitted actions; a real merchant response and ten qualified users are still outcomes to acquire, not implementation test results.
